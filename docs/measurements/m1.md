## Method

Every run uses release builds, made with their own `-p` build (CLAUDE.md):

```
cargo build --release -p turts_server
cargo build --release -p turts_client
cargo build --release -p turts_mod_runtime --bin turts-pack
(cd crates/turts_client_web && trunk build --release)
for f in crates/turts_client_web/dist/*.wasm crates/turts_client_web/dist/*.js; do
    brotli -q 11 -k -f "$f"
done
```

The package is `mods/base`, packed from a copy (`turts-pack` writes `<dir>.tar` next to the
directory):

```
cp -r mods/base target/m1/pack/base
target/release/turts-pack target/m1/pack/base       # target/m1/pack/base.tar
```

`server.ron` for each run: `game_package` is the packed archive, `http_listen` and `ws_listen`
are two free ports on `127.0.0.1`, `public_url` is `http://127.0.0.1:<http port>`,
`tick_hz: 20`. The browser runs add `static_dir: "<repository>/crates/turts_client_web/dist"`.
Each run uses a new server process and a new browser process (an empty browser cache).

### Figures 1 and 2 and the synthetic figure: bytes per tick, server tick p99 (native client behind the relay)

```
target/release/turts_server RUN/server.ron --stats RUN/stats.json [--synthetic-units 1000] &
python3 tests/net/relay.py <relay port> <ws port> --out RUN/relay.json &
target/release/turts_client --headless --server http://127.0.0.1:<http port> \
    --ws ws://127.0.0.1:<relay port> --run-secs 60 --out RUN/client.json \
    --frame-log RUN/client.frames [--move 20,8]
```

- One-unit run: no `--synthetic-units`, and the client sends `--move 20,8` once (the unit moves
  from (8, 8) to (20, 8), 80 ticks, in the first seconds). One run is one 60 s client run.
- Synthetic run: `--synthetic-units 1000` (1,000 units, each gets a new target every 40 ticks)
  and no `--move`. The frame log has one line per unit per frame (about 1,000 lines per
  frame), so the client writes it to `>(grep '^#' > RUN/client.header)` and only the summary
  line stays.
- `relay.py` counts the bytes of the TCP stream between the client and the server. The
  WebSocket frame headers, the lightyear and netcode headers, the pings, `Welcome` and the
  first `Snapshot` are all in the count. The HTTP download of the package does not pass the
  relay.
- `ticks` (the session ticks) = `latest_tick` of `RUN/client.json` (`debug.last_frame`) minus
  `welcome_tick` of the `# welcome_tick=..` line of the frame log. These are the ticks after
  `Welcome` that the client saw.
- `wire bytes per tick` = `to_client_bytes` (`relay.json`) / `ticks`.
- `payload per tick` = `delta_payload_bytes_total` (`stats.json`) / `ticks`.
- `overhead per tick` = `wire bytes per tick` - `payload per tick`.
- The stats line is the first line that the server wrote at or after the exit of the client
  (the server writes one line each second). The server runs until the harness stops it after
  that read.
- Server tick p99 and the other tick figures are `tick_p50_us`, `tick_p99_us`, `tick_max_us` of
  that line. They cover every tick of the process (1,220 ticks), including 14 to 16 ticks
  before `Welcome` and 8 to 10 ticks after the last tick that the client saw. A tick is the
  time from `FixedFirst` to the end of `FixedLast`: the simulation, the change collection and
  the sending of the deltas (`crates/turts_server/src/stats.rs`).

### Figures 3, 4 and 5: browser frame p99, wasm memory, download size

```
target/release/turts_server RUN/server.ron --stats RUN/stats.json [--synthetic-units 1000] &
cd tests/browser
node measure.js "http://127.0.0.1:<http port>/?server=http://127.0.0.1:<http port>&ws=ws://127.0.0.1:<ws port>" <label> [--enable-gpu --use-angle=gl]
```

`measure.js` waits for the first frame (`window.turts_debug()` returns text), reads Resource
Timing, and then records for 10 s:

- **Frame p99:** the 99th percentile of the `requestAnimationFrame` intervals, in ms. Bevy runs
  one frame for each call on wasm32. The page is 1280 x 720. The unit is not moving in the
  one-unit browser runs (`measure.js` sends no move).
- **Wasm memory high-water:** `window.turts_memory_bytes()` once each second, ten samples. The
  hook returns `memory_size(0) * 65536`. Wasm memory never shrinks, so the last sample is the
  high-water mark of the window (the first frame to 10 s after it).
- **Download size:** the sum of `transferSize` of the navigation entry and every resource entry
  at the first frame. The server sends the `.br` files (`ServeDir::precompressed_br`).

## Facts found

- The plan (Task 13 step 1, items 3 and 4) says to use `window.turts_debug` frame records for the
  frame p99. The debug JSON has no frame time: `last_frame` holds the bracket of the first unit
  (`t`, `lo_tick`, `hi_tick`, `fraction`, `latest_tick`). `measure.js` (Task 12) uses the
  `requestAnimationFrame` intervals. This record follows `measure.js`.
- `measure.js` reads memory from `window.turts_memory_bytes()`. Before this commit the hook did
  not exist and `measure.js` printed ten `null` samples (run on the `dist` that existed before
  the edit: `"wasmMemoryBytes": {"samples": [null, ...], "last": null}`). After the edit, it
  printed 38,535,168.
- The `gl` field of `measure.js` reads `getParameter(RENDERER)`. Chrome masks this value as
  `WebKit WebGL`, so the field cannot tell a SwiftShader run from a GPU run. The comment in
  `measure.js` says that it can. The renderer in this file comes from the separate probe above.
  `measure.js` is a Task 12 file; this task did not change it.
- With the GPU flags, `requestAnimationFrame` runs at 16.7 ms (60 Hz). The frame p99 of the GPU
  runs sits at this interval, so the figure shows that p99 frames kept the 60 Hz cadence and
  cannot show how much time was left in a frame.
- `measure.js` records the 10 s after the first frame. The memory figure covers that window. A
  longer run or a bigger match can grow wasm memory more; this file does not measure that.
- In the 1,000-unit browser runs, `turts_debug` rebuilds a JSON string of all units each frame
  (`crates/turts_client/src/debug.rs`, `rebuild_debug_state`), and the web crate copies it
  (`publish_debug`). The cost of this hook is part of those frame and memory figures. The
  one-unit runs have almost no such cost.
- The client sends 89 to 94 bytes per tick to the server in the one-unit runs (103 in the
  1,000-unit runs), with one move command in 60 s. The relay counts these bytes in
  `to_server_bytes`. The content of these bytes is not analysed here.
- The wire bytes include the handshake, `Welcome` and the first `Snapshot`. The server sends
  them once, at the start of the session. This file does not separate them from the per-tick
  overhead.
- The spike record (`m1-network-spike.md`, P5) gave 10,387.7 wire bytes per tick for 1,000 units
  over 60 s. It used the spike server, the spike client and the number of received deltas as
  divisor. The synthetic runs here use the real server, the real client and the session ticks as
  divisor, and give 10,368.3 to 10,420.1.

## Open budgets that these numbers feed

These are inputs for later decisions. Nothing here sets a budget.

- Spec 13: "Browser compatibility, memory, startup payload, script overhead, and network traffic
  all need budgets", and "Numeric latency, bandwidth, and other acceptance thresholds remain
  open". Figures 1 and 2 feed network traffic and tick time. Figures 3 to 5 feed browser
  frame time, memory and startup payload. Script overhead has no M1 figure (M1 packages have no
  script).
- Spec 13.2: the small scenario (4 players, 1,000 units, one map) on 4 vCPUs and 8 GB. These runs
  use one player on the machine above, not that allocation. Hosting figures need the GCP VM
  (M7).
- Spec 15 "Game scale" (acceptance thresholds), "Platform matrix" (WebGPU versus WebGL
  fallback, exact browsers, minimum client hardware) and "Networking" (update policies).
- Tick rate: 20 Hz is a prototype constant.
